OVERVIEW

What You Will Learn

In this article, you will learn how to set preprocessing and augmentation boundaries for your own images by watching every TorchVision operation run live — and copying out the exact code that produced what you see.

Topics we will cover include:

  • How the five core transforms move an image from JPEG to a normalized [C, H, W] tensor, and where each one destroys information you cannot get back.
  • How to set the boundaries of ColorJitter, RandomResizedCrop, and your own custom noise transforms by eye, with seeds that make every random draw reproducible.
  • How the same post-processing math — softmax top-5, confidence thresholds, per-pixel argmax — drives classification, detection, and segmentation models running directly in your browser.

There is a lot of ground to cover, so let's get started.

Introduction

An augmentation policy copied from a paper is a bet that your data looks like theirs. Brightness 0.4 is gentle on street scenes and garish on macro flower photography; a crop scale of 0.08 is standard for ImageNet and routinely produces subject-free tiles on portraits. The gap between what a transform does and how much of it your data can take is where silent accuracy loss lives — and no amount of reading closes it, because the judgment is visual.

TorchVision is PyTorch's vision toolkit, and it ships four things: transforms that reshape, rescale, and randomize images (Resize, CenterCrop, ToTensor, Normalize, and the Random* family); datasets such as CIFAR-10, EMNIST, your own folders via ImageFolder, and FakeData for debugging; models — pretrained networks for classification, detection, and segmentation; and utils for the visual bookkeeping — make_grid, save_image, draw_bounding_boxes, draw_segmentation_masks.

Each station below rebuilds one part of Module 2 as a live instrument. Drag a slider and the image reacts; the Python beside it rewrites itself with the values you chose, so the settings that look right on your data paste straight into your training script.

THE LIGHT TABLE

Tensors: What an Image Is to PyTorch

EXACT

decode_image() loads a JPEG or PNG into a tensor with dimensions ordered channels first — [C, H, W] — unlike Pillow and OpenCV, which put channels last. Values are uint8, 0–255. Hover the image and read the tensor at any pixel.

setup.py — the base every station shares
# run once — every station below only swaps the `transform = ...` line
from PIL import Image
import torch
from torchvision import transforms
from torchvision.transforms import InterpolationMode

img = Image.open("flower-1.jpg")        # PIL image · H×W×C

transform = transforms.Resize(224)       # ← the only line that changes
out = transform(img)                       # run it · PIL in → PIL out (until ToTensor)
shape [3, 360, 480] · dtype uint8
hover the image →

Why it works this way: convolutions in PyTorch expect [N, C, H, W] batches, so TorchVision stores images the way the model will consume them.

Limitations: uint8 is compact, but no model consumes it directly — every pipeline ends in float32. Mixing up HWC and CHW is the single most common shape bug in Module 2, and it fails at the first Conv2d, not at load time. Station 02 makes the conversion.

CORE TRANSFORMS

The Five Core Transforms: JPEG In, Tensor Out

EXACT

Preprocessing means getting every image to the same size, format, and scale, because a batch cannot be stacked — and a pretrained backbone cannot be trusted — until they match. These five transforms do almost all of that work.

Use it when a fixed-size network needs standardized inputs, or a pretrained backbone expects the resolution it was trained at. The single-int rule: Resize(224) resizes the smaller edge to 224 and scales the other proportionally, so the aspect ratio survives.

Limitations: detail lost below the resolution floor does not come back — drag under ~50 and watch it go. And because single-int mode preserves aspect ratio, the output is not square; pair it with a crop before batching.

bilinear here is implemented by hand (not the browser's), matching PIL's sampling
transform.py — what changes
transform = transforms.Resize(224)

Use it when validation and inference need deterministic framing — the classic pair is Resize(256) then CenterCrop(224), keeping the central portion at a fixed size.

Limitations: the crop discards edges unconditionally — usually background, sometimes your subject. Shrink it until you start losing things you care about; that is your boundary. It has no randomness, so it does not augment: for training variety, reach for RandomResizedCrop in station 03.

after Resize
after CenterCrop
transform.py — what changes
transform = transforms.Compose([
    transforms.Resize(256),
    transforms.CenterCrop(224),
])

Use it when — always, exactly once, at the boundary between image-space transforms and tensor math. It divides every value by 255 so pixels live in 0–1 and reorders H×W×C → C×H×W. The picture does not change; only its numeric representation does. ToPILImage() is the exact inverse, with no loss.

Limitations: position matters more than the operation — the classic transforms expect PIL images, so anything placed after ToTensor() except Normalize() raises a TypeError. Station 05 lets you trigger that error on purpose.

PIL / uint8 · HWC
tensor / float32 · CHW
the same 4 pixels from the image centre, in both representations
transform.py — what changes
transform = transforms.ToTensor()   # /255 → float32, and HWC → CHW
back = transforms.ToPILImage()(out)   # the exact inverse, no loss

Use it when feeding a pretrained backbone — use the ImageNet statistics it was trained with — or training from scratch, where you compute mean and std from your own data. Normalize is a per-channel z-score: subtract the mean, divide by the std. The histograms are the honest view — same shapes, recentred at 0 with σ≈1.

Limitations: the output is no longer an image. It has negative values, so it cannot be displayed or saved without undoing the operation — the preview above is min-max rescaled and labelled as such. Wrong statistics do not raise an error; they silently shift every input off the distribution the backbone learned. That failure mode is invisible until accuracy tells you.

normalized · rescaled for display ⚠
before — pixel intensity per channel (0–1)
after — z-scores per channel (≈ −3 to 3, centred on 0)
transform.py — what changes
transform = transforms.Compose([
    transforms.ToTensor(),                 # Normalize needs a tensor first
    transforms.Normalize(mean=[0.485, 0.456, 0.406],
                         std=[0.229, 0.224, 0.225]),
])

AUGMENTATION

Random Transforms: One Image, Many Samples

EXACT

A small dataset is the usual reason to augment: each random variation is effectively a new training sample, teaching the model that the label survives the change. The Random* transforms roll fresh dice on every call — here the dice are a seed you control, the same trick as torch.manual_seed(). Same seed, same "random" result.

Use it when lighting or camera variance is expected at test time. Each slider sets a range: brightness 0.4 means a factor drawn uniformly from [0.6, 1.4]. TorchVision implements each as a blend — brightness with black, contrast with the grey mean, saturation with the grayscale — and that exact blend math runs here. Your boundary is wherever a draw stops looking like plausible data.

Limitations: color is label information for some tasks — species identified by hue, ripeness, medical staining — and jitter can erase exactly what the model needs to learn. The three factors are also sampled independently, so worst-case combinations do occur; the grid shows you four at a time for that reason.

4 samples from the current jitter ranges (factors printed on each tile)
transform.py — what changes
torch.manual_seed(7)
transform = transforms.ColorJitter(brightness=0.4, contrast=0.4, saturation=0.4)

Use it when orientation does not define the object — true for most natural photos. Default p=0.5: half of all samples get mirrored.

Limitations: when orientation is semantic — digits, text, road signs — a flip manufactures a wrongly-labelled sample. And p is a per-sample probability, not a guarantee: at p=0.5, a run of six unflipped draws is unlikely but legal, as the seed control will show you.

6 draws · amber corner = this draw flipped
transform.py — what changes
torch.manual_seed(7)
transform = transforms.RandomHorizontalFlip(p=0.5)

Use it when you want scale and translation invariance — this is the standard ImageNet training crop. It samples a random area (between scale min and 100%, at a random aspect ratio 3/4–4/3) and resizes it to the output size, using TorchVision's exact 10-attempt sampling logic.

Limitations: at a low scale minimum, crops can miss the subject entirely — push it to 0.08 and watch subject-free tiles appear. Each one is a mislabelled training sample. The outlines on the original show you precisely which regions the sampler chose; that is the boundary you are here to find.

4 draws · outline on the original shows each sampled region
transform.py — what changes
torch.manual_seed(7)
transform = transforms.RandomResizedCrop(224, scale=(0.30, 1.0))

CUSTOM TRANSFORMS

Custom Transforms: Writing Your Own Noise

EXACTAPPROX (Poisson)

When a transform does not exist, you write a class with __init__ (parameters) and __call__ (the operation) and drop it into the pipeline like any other — TorchVision only requires that it is callable. The classic example: salt-and-pepper noise, random white and black pixels simulating a grainy sensor.

Use it when deployment noise is predictable and you can name its physics: salt & pepper ≈ dead pixels and transmission errors, Gaussian ≈ general sensor degradation, Poisson ≈ low-light shot noise. Training on the noise you expect is cheaper than cleaning it at inference.

Limitations: noise you will not see in production is pure signal destruction — it slows training and buys nothing. Past a certain amount the subject itself degrades, not just the pixels; the slider will show you where. And the Poisson option here is a Gaussian approximation (σ = √signal) — visually faithful, statistically approximate.

custom_transform.py — __init__ + __call__, then swap it in
class SaltAndPepperNoise:
    def __init__(self, ratio=0.5, amount=0.05):   # parameters live here
        self.ratio, self.amount = ratio, amount
    def __call__(self, img):                      # the operation lives here
        arr = np.array(img)
        n = int(arr.shape[0] * arr.shape[1] * self.amount)
        ys, xs = np.random.randint(0, arr.shape[0], n), np.random.randint(0, arr.shape[1], n)
        arr[ys, xs] = np.where(np.random.rand(n, 1) < self.ratio, 255, 0)
        return Image.fromarray(arr)

transform = SaltAndPepperNoise(ratio=0.5, amount=0.050)

Compose: Order Is Part of the Pipeline

Compose is a list of transforms applied in order, and the order is part of the specification — the same stages in a different sequence are a different pipeline. make_grid: Where the Boundary Decision Gets Made

Run the whole pipeline several times with different seeds and tile the results — exactly what make_grid(nrow, padding, normalize) does for a batch. The test is simple: if any tile looks like garbage data, tighten the stage that produced it. This sheet is where the augmentation-boundary decision actually gets made.

Use it when you want to see a batch the way the model will — especially after Normalize(), where raw z-score tensors are unviewable without normalize=True rescaling them. The download button is real: canvas → PNG, the browser's save_image().

Limitations: normalize=True min-max rescales per grid, so brightness is comparable within one sheet but not across sheets. Toggle it to False after normalizing and the tiles go dark — that is not a bug, that is what your tensors look like.

6 pipeline runs · seeds seed+0 … seed+5
contact_sheet.py — what changes
from torchvision.utils import make_grid, save_image

batch = torch.stack([transform(img) for _ in range(6)])
grid  = make_grid(batch, nrow=3, padding=4, normalize=True)
save_image(grid, "contact_sheet.png")

BOUNDING BOXES

draw_bounding_boxes: Annotation Is Just a Tensor

EXACT

A bounding box is four numbers — [x1, y1, x2, y2] in absolute pixels — plus a label, and draw_bounding_boxes just paints them. Drag a box to move it, drag its corner dot to resize, and watch the coordinate tensor update. This is the manual annotation flow from the notes, before any model is involved.

Limitations: coordinates are absolute pixels. Resize the image and the boxes do not follow — which is exactly why detection pipelines must transform boxes and images together, and why the augmentation transforms above cannot be reused as-is for detection data.

DATASETS

Datasets: FakeData, and Why EMNIST Is Upside-Down

EXACTDIAGRAM (downloads)

TorchVision ships pre-built datasets (CIFAR-10, EMNIST, COCO…), loads your own folders via ImageFolder, and generates FakeData for pipeline debugging. Real downloads cannot run in a static page — but the two ideas that are pure computation run below.

FakeData() — debug the shape, not the content

Use it when you want to debug the plumbing before the data arrives: random tensors that mimic your real data's shape. If your model accepts this batch, the shapes are right — and you have not downloaded a single real image yet.

Limitations: FakeData proves shapes, nothing else. There is no signal in noise, so loss curves and accuracy on it mean nothing — the moment the plumbing works, switch to real data.

fake_data.py — what changes
from torchvision.datasets import FakeData
ds = FakeData(size=8, image_size=(3, 32, 32), transform=transforms.ToTensor())

EMNIST's documented fix: rotate 90° + vertical flip

EMNIST images are stored transposed, so its documented preprocessing rotates 90° and flips vertically before normalizing (mean=std=0.5). Draw a digit: the middle panel shows how EMNIST stores it, the right panel shows the fix recovering it.

Limitations of skipping it: nothing fails. The model trains happily on transposed digits, the loss goes down, and then it cannot read yours — a reminder that datasets carry conventions the tensors do not announce.

as stored on disk
rot90 + vflip → correct
emnist_fix.py — the documented preprocessing
transform = transforms.Compose([
    lambda im: transforms.functional.rotate(im, 90),   # torchvision rotates counter-clockwise
    lambda im: transforms.functional.vflip(im),
    transforms.ToTensor(),
    transforms.Normalize((0.5,), (0.5,)),
])

TRANSFER LEARNING

Transfer learning — freeze the backbone, swap the head

DIAGRAM

Early layers learn generic features — edges, textures, shapes — useful for any vision task. So: freeze them, replace the final layer with one sized for your classes, and train only that. A browser cannot train a network, so this station is a diagram — toggle the two decisions that define the technique.

Use it when your dataset is small and your domain is close to the pretraining data — transfer learning gets you a working classifier from hundreds of images, not tens of thousands.

Limitations: frozen features cap accuracy when the domain shifts — ImageNet edges transfer to flowers better than to X-rays, and fine-tuning with too high a learning rate can destroy the pretrained features you froze everything to protect. One architectural detail does real damage: the head is model.fc on ResNet but model.classifier[-1] on MobileNet — replace the wrong attribute and you train a layer the forward pass never uses.

WRAPPING UP

Wrapping Up

An augmentation policy is not a recipe you copy; it is three questions you answer about your own data, and every answer is checkable on this page.

Does orientation or color carry label information? If yes — digits, signage, species identified by hue — restrict flips and jitter before they manufacture wrongly-labelled samples. If no, they are the cheapest data you will ever generate.

At your crop scale, do the contact-sheet tiles still contain the subject? Run station 05 with six seeds and look. The largest scale minimum that never loses the subject is your setting; anything lower trades real samples for noise.

Is a pretrained backbone involved? Then its normalization statistics are not a choice — use the mean and std it was trained with, and keep Resize → CenterCrop → ToTensor → Normalize in that order for evaluation.

Start with the deterministic pipeline, add one random transform at a time, and widen its range only when the contact sheet says the data can take it. The transforms will not tell you when you have gone too far. The sheet will.

Appendix: What Is Exact and What Is Not

Interactivity is only useful if it does not quietly lie to you. What is exact, what is approximate, and what is a stand-in:

featurefidelitydetail
ToTensor / CenterCrop / flip / make_grid / cropsEXACTPure integer/float arithmetic, identical to TorchVision.
NormalizeEXACTTrue per-channel z-score; only the on-screen preview is rescaled (and labelled).
ColorJitterEXACTTorchVision's blend formulas (black / grey-mean / grayscale) reimplemented.
Resize (bilinear)APPROXHand-written bilinear sampling; PIL adds antialiasing on downscale, so pixels can differ by a few values.
Poisson noiseAPPROXGaussian approximation with σ = √signal.
Random* samplingEXACTSame sampling logic (incl. RandomResizedCrop's 10-attempt loop); different RNG stream than torch, so seeds match themselves, not torch's.
Classification / detection / segmentationLIVEReal networks, MobileNet backbones instead of ResNet — fetched from a CDN only on demand.
