Paper Notes · Radford et al., 2019

GPT-2: When Next-Token Prediction Becomes Multitask Learning

GPT-1 needed a fine-tuning run for every task. A year later, OpenAI asked a bolder question: if a language model is big enough and reads enough of the web, does it still need the fine-tuning at all?

GPT-2 Paper Notes Transformers Zero-shot Language Modeling
01

The takeaway first

TL;DR

GPT-1 showed that pretraining (training on large number of books) a language model and then fine-tuning it works across many tasks. GPT-2 asks whether a much larger model, trained on a much broader corpus, can begin to do those tasks without any task-specific fine-tuning.

02

Motivation

From narrow task models to one general language model

NLP systems of the time were built around one labeled dataset and one objective. They did very well on test sets drawn from the same distribution, and broke easily outside it. The authors call these systems "narrow experts", and they are clear about where they think the brittleness comes from:

"Our suspicion is that the prevalence of single task training on single domain datasets is a major contributor to the lack of generalization observed in current systems."

If narrow training is what hurts generalization, the fix is to train broadly. GPT-2 starts from that ambition: one model should learn enough about language that many tasks can be expressed directly through text, with no dedicated finetuning.

The key observation is that the internet already contains natural demonstrations of many tasks: translation pairs, questions and answers, summaries, definitions and explanations. A model trained only to predict the next token still benefits from learning these patterns, because doing so lowers its loss. A single-task system only learns to map an input to an output. A general system also has to know which task it is being asked to do, and GPT-2's bet is that the task can simply be described in text.

GLUE vs DecaNLP

The paper positions itself against two multitask benchmarks of the time.

Benchmark suite

GLUE

A shared set of language-understanding tasks such as entailment, paraphrase detection, acceptability and similarity. Each task keeps its own native format.

Unified format

DecaNLP

Goes further by casting ten different NLP tasks into one question-answering, text-to-text interface.

Training data

WebText: a deliberately broad corpus

GPT-1 read 7000 books. For GPT-2 the authors went ahead with web pages which contains long contiguous text across domains. They built WebText, a new corpus: the pages behind outbound Reddit links that received at least 3 karma. Reddit votes act as a rough human quality filter. Links that people chose to share and upvote are more likely to hold useful or interesting text. Wikipedia was removed on purpose to avoid overlapping with evaluation datasets.

04

Input representation

Why GPT-2 moved to byte-level BPE

A general language model should be able to assign a probability to any string. And the NLP techniques often used preprocessing steps like lowercasing and stemming, restricting the space of modelable strings. Playing with UNICODE representation of characters was an elegant way to handle this as it contains ~150K characters and can represent any language. However, character level encoding is inefficient. Modeling raw bytes avoids the problem, since every Unicode string can be encoded with only 256 possible byte values, but byte sequences are long and slow to model.

GPT-2 uses byte-level BPE to get both. It starts from bytes, then learns merges that combine frequently co-occurring byte sequences into larger tokens. Every string can still be encoded, and common words still end up as single tokens. The resulting vocabulary has 50,257 tokens.

Step 1 · characters → Unicode code points

Take a small string with plain English, punctuation and an emoji, and look up each character's code point with ord:

code points · python
text = "Hello World!😀"
dict((c, ord(c)) for c in text)
output
{'H': 72, 'e': 101, 'l': 108, 'o': 111, ' ': 32, 'W': 87,
 'r': 114, 'd': 100, '!': 33, '😀': 128512}

English letters sit below 128, but the emoji is code point 128,512. A model that used code points directly would need a slot for every one of them, and Unicode is huge:

size of unicode · python 3.13
import sys, unicodedata

sys.maxunicode + 1   # every possible code point

# characters actually assigned (not unassigned, private-use or surrogates)
sum(unicodedata.category(chr(i)) not in ("Cn", "Co", "Cs")
    for i in range(sys.maxunicode + 1))
output
1114112
149878

That is a base vocabulary of roughly 150,000 symbols before a single merge is learned, and most of them appear so rarely that the model could never learn good embeddings for them.

Step 2 · code points → UTF-8 bytes

Now encode the same string as UTF-8 and look at the raw bytes:

bytes · python
text.encode('utf-8')
text_bytes = list(text.encode('utf-8'))
text_bytes
dict((c, chr(c)) for c in text_bytes)
output
b'Hello World!\xf0\x9f\x98\x80'

[72, 101, 108, 108, 111, 32, 87, 111, 114, 108, 100, 33, 240, 159, 152, 128]

{72: 'H', 101: 'e', 108: 'l', 111: 'o', 32: ' ', 87: 'W', 114: 'r',
 100: 'd', 33: '!', 240: 'ð', 159: '\x9f', 152: '\x98', 128: '\x80'}

Three things to notice:

  • The English characters map to one byte each, with the same numbers as their code points.
  • The emoji becomes four bytes: 240 159 152 128. So 13 characters turn into 16 bytes.
  • On their own, those four bytes are meaningless (chr(240) is 'ð'). They only mean 😀 when read together.

Every value from 0 to 255. Any string in any language fits, so nothing is ever unknown.

Step 3 · BPE merges bytes back into useful chunks

Bytes solve coverage but make sequences longer. BPE fixes that. It counts every adjacent pair of symbols in the training data, merges the most frequent pair into a new symbol with the next free ID (256, 257, …), and repeats. Here are four merges applied to our example:

bpe merges · python
def merge(ids, pair, new_id):
    out, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and (ids[i], ids[i+1]) == pair:
            out.append(new_id); i += 2
        else:
            out.append(ids[i]); i += 1
    return out

# pretend these were the most frequent pairs in a large corpus
merges = [(108, 108), (240, 159), (257, 152), (258, 128)]

ids = text_bytes
for new_id, pair in enumerate(merges, start=256):
    ids = merge(ids, pair, new_id)
    print(new_id, pair, len(ids), ids)
output
256 (108, 108) 15 [72, 101, 256, 111, 32, 87, 111, 114, 108, 100, 33, 240, 159, 152, 128]
257 (240, 159) 14 [72, 101, 256, 111, 32, 87, 111, 114, 108, 100, 33, 257, 152, 128]
258 (257, 152) 13 [72, 101, 256, 111, 32, 87, 111, 114, 108, 100, 33, 258, 128]
259 (258, 128) 12 [72, 101, 256, 111, 32, 87, 111, 114, 108, 100, 33, 259]

Merge 256 turns "ll" into one token. Merges 257 to 259 glue the four emoji bytes back together, so 😀 is a single token again (ID 259). The sequence shrinks from 16 to 12 symbols, and the vocabulary only grows by the merges we choose to keep.

In a 13-character string every pair appears once, so the merges above are picked by hand. On 40 GB of WebText the counts are real, and the frequent pairs are things like common word pieces, spaces before words, and popular emoji. GPT-2 keeps 50,000 merges, which is where its vocabulary size comes from:

$$256\ \text{bytes} + 50{,}000\ \text{merges} + 1\ \text{end-of-text token} = 50{,}257\ \text{tokens}$$

One tweak from the paper: BPE is not allowed to merge across character categories, so letters don't fuse with punctuation. Without this, the vocabulary fills up with variants like dog., dog! and dog?. Spaces are the exception, which is why many GPT-2 tokens include a leading space.

How GPT-1 did it: spaCy, then character-level BPE

GPT-1 took a more traditional route. It cleaned BooksCorpus with the ftfy library, then ran the spaCy tokenizer to split the text into words and punctuation (for example Hello World! → Hello · World · !). BPE with 40,000 merges was then learned on top of those words, starting from characters rather than bytes.

That works well for clean English books, but the base alphabet is whatever characters showed up in training. A character it never saw has no symbol at all. Starting from bytes removes that failure mode and also drops the dependence on a language-specific pre-tokenizer like spaCy.

Architecture

GPT-1's architecture, scaled and stabilized

There is no new architecture here. GPT-2 keeps the decoder-only Transformer from GPT-1 and makes a few changes:

  • Layer norm moves to the input of each sub-block, and one extra layer norm is added after the final block.
  • Initialization changes to stay stable as the stack gets deeper.
  • The context window doubles from 512 to 1,024 tokens.
  • Batch size grows to 512.

Every size keeps the same head width:

$$d_{\text{head}} = \frac{d_{\text{model}}}{n_{\text{heads}}} = \frac{768}{12} = \frac{1600}{25} = 64$$
A correction to Table 2 The parameter counts printed in the paper, 117M, 345M, 762M and 1542M, are not the sizes of the released models. The layer, head and width columns are right. Only the parameter column is off, and the table above uses the corrected numbers.

BEFORE BENCHMARKING

A nuance before benchmarking

GPT-2 is still doing language modeling, just on datasets it was never trained on. The difficulty is that each benchmark uses its own tokenizer and reports results in its own units.

What is a "canonical prediction unit"?

Raw negative log-likelihood grows with the length of the dataset, so benchmarks normalize it by a standard unit, usually a word, a character or a byte:

$$\text{average loss} = \frac{-\log p(\text{dataset})}{N}$$
\(N\)
the number of canonical units (words, characters or bytes) in the benchmark

Perplexity is then derived from this normalized loss. Because the denominator is fixed by the benchmark, models with different internal tokenizers can be compared fairly.

Why invertible de-tokenizers?

Older benchmarks often ship with artificial preprocessing:

Tokenized benchmark → natural text
Idon'tlikeit. → I don't like it.

GPT-2 was trained on natural web text, so that spacing looks strange to it. An invertible de-tokenizer removes these artifacts while keeping a one-to-one mapping back to the benchmark's format, so likelihood can still be computed correctly. The paper reports roughly 2.5 to 5 perplexity points of improvement from this step alone.

Result Without seeing a single training example from these datasets, the largest GPT-2 reaches state of the art on 7 of 8 language-modeling benchmarks. The exception is One Billion Word, whose sentence-level shuffling destroys the long-range structure GPT-2 is good at.
Glossary
Negative log-likelihood
How surprised the model is by the real text; lower is better.
Perplexity
Roughly, how many options the model is torn between at each step; lower is better.
Invertible de-tokenizer
A script that undoes this odd spacing in a way that can be reversed exactly.

Experiments · Cloze tasks

CBT and LAMBADA: filling the blank, near and far

Children's Book Test

CBT is a multiple-choice cloze task: one word is removed from a passage and the model picks it from ten candidates. Results are reported by word type. The largest GPT-2 reaches about 93.3% on common nouns and 89.1% on named entities.

Before scoring, the authors remove PTB-style tokenization artifacts. PTB is Penn Treebank tokenization, which turns natural text such as I don't know. into I do n't know .. The de-tokenizer restores the natural form before GPT-2 sees it.

LAMBADA

LAMBADA asks the model to predict the last word of a passage, where a human can only guess it after reading the wider context. It tests long-range dependencies directly.

Experiments · Reasoning & reading

Winograd and reading comprehension

On the Winograd Schema Challenge, a test of commonsense pronoun resolution, GPT-2 reaches 70.70% accuracy, about seven points above the previous state of the art reported in the paper. The benchmark has only 273 examples, so take the margin with some caution.

On CoQA, conversational question answering, GPT-2 gets the document, the dialogue history and a final A: as a cue to start answering:

CoQA prompt zero-shot
document Q: … A: … Q: new question A: → generated answer

It reaches 55 F1 without using any of the 127,000+ supervised training examples. That matches or beats 3 of the 4 baseline systems, but it is still far below humans and strong supervised models.

What is an extractive, pointer-network style answer?

Instead of generating an answer freely, an extractive QA model predicts where the answer starts and ends inside the passage, like a pointer network:

$$P(\text{start} = i), \qquad P(\text{end} = j)$$

For "Marie Curie was born in Warsaw", it can point straight at Warsaw. GPT-2 is generative. It writes the answer token by token and is not limited to copying a span, which is both more flexible and easier to get wrong.

Glossary
Pronoun resolution
Working out who or what words like “it” or “they” refer to.
Extractive QA
One that can only copy its answer out of the passage.
Pointer network
A model that answers by pointing at positions in its input.

What is ROUGE F1?

ROUGE-1 measures unigram overlap with a reference summary, ROUGE-2 bigram overlap, and ROUGE-L the longest common subsequence. F1 balances precision and recall:

$$F_1 = \frac{2PR}{P + R}$$
Caveat ROUGE measures word overlap. It does not check whether a summary is factually correct or means the same thing as the reference.

Experiments · Translation

Translation from almost no French

To get GPT-2 to translate, the authors condition it on example pairs in the form english sentence = french sentence, then give it a new English sentence followed by =. Quality is measured with BLEU.

Translation prompt few example pairs
english=french english=french new english= → french
English → French

~5 BLEU

Weak. Producing fluent French is hard for a model that has seen very little of it.

French → English

~11.5 BLEU

Much stronger, because GPT-2 is a far better English language model.

How little French was there?

A footnote points to CLD2 (Compact Language Detector 2), an existing open-source language identifier that uses lightweight statistics over byte and character sequences. The authors used it to estimate that only about 10 MB of WebText was French:

$$\frac{10\ \text{MB}}{40{,}000\ \text{MB}} \approx 0.025\%$$

So explicit French was a tiny sliver of the corpus, and the model still picked up enough to translate a little.

Glossary
BLEU
A 0 to 100 score of how closely the output matches human translations.

Experiments · Question answering

Knowledge stored in the parameters

On Natural Questions, GPT-2 is seeded with example question and answer pairs and then asked new factual questions, with no passage to read from. Whatever it answers has to come from its weights.

The largest model gets roughly 4.1% exact match. That is poor next to dedicated open-domain QA systems, but it is real evidence that facts learned during language modeling can sometimes be pulled straight out of the parameters.

The pattern that keeps repeating The smallest GPT-2 does not even beat a trivial baseline that answers based on question type. The largest one does. Across the paper, capabilities that smaller models barely show start to appear as the model grows.
Glossary
Natural Questions
Real questions people typed into Google.
Open-domain QA
Answering questions on any topic, usually by searching documents first.

Generalization vs memorization

Did GPT-2 just see the test set?

A zero-shot result means little if the test examples were already in the training data. With 40 GB of web text, that is a fair worry. The authors check overlap between WebText and public benchmarks using a Bloom filter over normalized 8-grams.

Bloom filters trade exact storage for compact, probabilistic lookup. They can give false positives, never false negatives.

How would you build one?

Normalize the training text, cut it into 8-word shingles, hash each shingle into the filter, then query the evaluation shingles with the same normalization.

minimal concept · python
from pybloom_live import BloomFilter

bf = BloomFilter(capacity=10_000_000, error_rate=0.001)

def ngrams(text, n=8):
    words = text.lower().split()
    return [" ".join(words[i:i+n])
            for i in range(len(words)-n+1)]

for gram in ngrams(training_text):
    bf.add(gram)

"We generated 1M strings, of which zero were found by the filter"

This is a sanity check for false positives. Query the filter with a million strings that should not be in it. Any hit would be a false positive, and they saw none. That does not prove the true rate is zero, only that it is very low.

Why 8-grams? My reading The paper states the choice of 8-grams but gives no ablation or explicit reason for it. A reasonable interpretation is that eight words are long enough to avoid accidental matches on common phrases, and short enough to still catch copied passages.

Discussion

What GPT-2 changes conceptually

The paper treats unsupervised task learning as something worth studying in its own right. Pretraining may do more than produce reusable representations: at enough scale, the language-modeling objective can itself produce useful task behavior.

The strongest evidence is the scaling trend. Small models often sit near trivial baselines, and larger ones cross into visibly useful behavior. Yet even the largest model still underfits WebText, so the paper does not claim that 1.5B parameters is anywhere near the ceiling.

Why mention "the prior success of fine-tuning GPT"? That is a reference to GPT-1, which established pretrain → supervised fine-tune. GPT-2 deliberately tests pretrain → prompt → zero-shot. The discussion suggests combining the two: GPT-2-scale pretraining followed by fine-tuning on multitask benchmarks such as DecaNLP and GLUE.

A quick refresher: GPT-1 in one table

Property GPT-1
Parameters ~117M
Layers 12

Attention heads 12

GPT-1's fine-tuning updates the whole Transformer, not just a small classifier head, and it can keep the language-modeling loss as an auxiliary objective during supervised training:

$$L = L_{\text{supervised}} + \lambda\, L_{\text{LM}}$$

Wrapping up

My Learnings

GPT-2's lasting contribution is not just that a 1.5B-parameter Transformer wrote better text. It is the argument that language modeling, given diverse enough data and enough capacity, becomes a general task-learning mechanism.

The recipe in one line
diverse text+ next-token prediction+ large Transformer→ implicit multitask learning
  1. Data quality can be crowdsourced. A 3-karma threshold on Reddit links was enough to build a broad, reasonably clean 40 GB corpus.
  2. Tokenization is part of generality. Byte-level BPE means the model can assign a probability to any string, with no unknown tokens.
  3. A prompt can define the task. TL;DR:, A: and english = french turned a language model into a summarizer, a reader and a translator.
  4. Scale unlocks behavior. On most tasks the smallest model is near baseline and the largest is not, and it still underfits its data.
  5. Always check for leakage. The Bloom-filter analysis is a habit worth copying for any model trained on web data.
