Paper Notes · Radford et al., 2019

GPT-2: When Next-Token Prediction Becomes Multitask Learning

GPT-1 needed a fine-tuning run for every task. A year later, OpenAI asked a bolder question: if a language model is big enough and reads enough of the web, does it still need the fine-tuning at all?

The takeaway first

TL;DR

GPT-1 showed that pretraining (training on large number of books) a language model and then fine-tuning it works across many tasks. GPT-2 asks whether a much larger model, trained on a much broader corpus, can begin to do those tasks without any task-specific fine-tuning.

02

Motivation

From narrow task models to one general language model

NLP systems of the time were built around one labeled dataset and one objective. They did very well on test sets drawn from the same distribution, and broke easily outside it. The authors call these systems "narrow experts", and they are clear about where they think the brittleness comes from:

"Our suspicion is that the prevalence of single task training on single domain datasets is a major contributor to the lack of generalization observed in current systems."

If narrow training is what hurts generalization, the fix is to train broadly. GPT-2 starts from that ambition: one model should learn enough about language that many tasks can be expressed directly through text, with no dedicated finetuning.

The key observation is that the internet already contains natural demonstrations of many tasks: translation pairs, questions and answers, summaries, definitions and explanations. A model trained only to predict the next token still benefits from learning these patterns, because doing so lowers its loss. A single-task system only learns to map an input to an output. A general system also has to know which task it is being asked to do, and GPT-2's bet is that the task can simply be described in text.

Training data

WebText: a deliberately broad corpus

GPT-1 read 7000 books. For GPT-2 the authors went ahead with web pages which contains long contiguous text across domains. They built WebText, a new corpus: the pages behind outbound Reddit links that received at least 3 karma. Reddit votes act as a rough human quality filter. Links that people chose to share and upvote are more likely to hold useful or interesting text. Wikipedia was removed on purpose to avoid overlapping with evaluation datasets.

04

Input representation

Why GPT-2 moved to byte-level BPE

A general language model should be able to assign a probability to any string. And the NLP techniques often used preprocessing steps like lowercasing and stemming, restricting the space of modelable strings. Playing with UNICODE representation of characters was an elegant way to handle this as it contains ~150K characters and can represent any language. However, character level encoding is inefficient. Modeling raw bytes avoids the problem, since every Unicode string can be encoded with only 256 possible byte values, but byte sequences are long and slow to model.

GPT-2 keeps GPT-1's core idea, BPE, but changes what it runs on. GPT-1 cleaned its text with ftfy, split it into words with the spaCy tokenizer, and learned 40,000 merges starting from characters, so a character it never saw in training had no symbol at all. GPT-2 drops the cleanup and the English-specific pre-tokenizer, and runs BPE directly on raw UTF-8 bytes. Any string can now be encoded, and 50,000 merges give a vocabulary of 50,257 tokens (256 bytes + 50,000 merges + 1 end-of-text token). The one rule it adds is that BPE can't merge across character categories, so dog., dog! and dog? don't each take up a vocabulary slot.

Why bytes win Unicode has over 1.1 million possible code points, about 150K of them assigned. Bytes have 256. An emoji like 😀 is code point 128,512, but in UTF-8 it is just four bytes, 240 159 152 128, and BPE can merge those back into a single token if it shows up often enough.

Architecture

GPT-1's architecture, scaled and stabilized

There is no new architecture here. GPT-2 keeps the decoder-only Transformer from GPT-1 and makes a few changes:

  • Layer norm moves to the input of each sub-block, and one extra layer norm is added after the final block.
  • Initialization changes to stay stable as the stack gets deeper.
  • The context window doubles from 512 to 1,024 tokens.
  • Batch size grows to 512.

BEFORE BENCHMARKING

A nuance before benchmarking

Before the results, the paper explains how it evaluates GPT-2 on existing language-modeling benchmarks. GPT-2 is still predicting the next token, just on datasets it was never trained on. Two problems come up straight away: every benchmark reports its score in its own unit, and many benchmarks have been preprocessed in ways that look nothing like the web text GPT-2 learned from. The paper puts it like this:

What the paper says

"Results on language modeling datasets are commonly reported in a quantity which is a scaled or exponentiated version of the average negative log probability per canonical prediction unit, usually a character, a byte, or a word."

"For many of these datasets, WebText LMs would be tested significantly out-of-distribution, having to predict aggressively standardized text, tokenization artifacts such as disconnected punctuation and contractions, shuffled sentences, and even the string <UNK> […] We report our main results using invertible de-tokenizers which remove as many of these tokenization / pre-processing artifacts as possible."

Canonical prediction unit: the benchmark's official unit

GPT-2 splits text into its own BPE tokens, other models split it into words or characters, so "loss per token" means something different for each model. To compare them, every benchmark fixes one official unit (its canonical unit) and everyone divides by that, whatever their tokenizer does internally.

So GPT-2 computes the total log-probability of the whole test set, then divides by the number of canonical units in it:

$$\text{average loss} = \frac{-\log p(\text{dataset})}{N}$$
\(N\)
the number of canonical units (words, characters or bytes) in the benchmark

For example, if a word-level benchmark contains the sentence the cat sat, GPT-2 might spend four BPE tokens on it, but \(N\) is still 3 words. Perplexity is then derived from this per-word loss. Because the denominator is fixed by the benchmark, models with completely different tokenizers can be compared fairly.

Invertible de-tokenizer: undo the benchmark's preprocessing

Many older benchmarks were tokenized before release, with punctuation and contractions split off by spaces:

Tokenized benchmark → natural text
Idon'tlikeit. → I don't like it.

GPT-2 almost never saw text like that on the web. Some benchmarks even replace rare words with the literal string <UNK>, which appears only 26 times in 40 billion bytes of WebText. The model ends up penalized for not predicting formatting quirks rather than language.

A de-tokenizer is a small script that turns the benchmark text back into natural text. It has to be invertible: there must be an exact, one-to-one way back to the original benchmark format. That way GPT-2 reads natural text, but the probability can still be counted against the official benchmark text and its canonical units, so the score stays comparable. The paper calls this a simple form of domain adaptation, and reports 2.5 to 5 perplexity points of improvement from it.

Result Without seeing a single training example from these datasets, the largest GPT-2 reaches state of the art on 7 of 8 language-modeling benchmarks. The exception is One Billion Word, whose sentence-level shuffling destroys the long-range structure GPT-2 is good at.

Generalization vs memorization

Did GPT-2 just see the test set?

A zero-shot result can be contaminated if the test examples were already in the training data. With 40 GB of web text, that is a fair worry. The authors check overlap between WebText and public benchmarks using a Bloom filter over normalized 8-grams.

Bloom filters trade exact storage for compact, probabilistic lookup. They can give false positives, never false negatives.

How would you build one?

Normalize the training text, cut it into 8-word shingles (overlapping chunks), hash each shingle into the filter, then query the evaluation shingles with the same normalization.

minimal concept · python
from pybloom_live import BloomFilter

bf = BloomFilter(capacity=10_000_000, error_rate=0.001)

def ngrams(text, n=8):
    words = text.lower().split()
    return [" ".join(words[i:i+n])
            for i in range(len(words)-n+1)]

for gram in ngrams(training_text):
    bf.add(gram)

"We generated 1M strings, of which zero were found by the filter"

This is a sanity check for false positives. Query the filter with a million strings that should not be in it. Any hit would be a false positive, and they saw none. That does not prove the true rate is zero, only that it is very low.

Why 8-grams? My reading The paper states the choice of 8-grams but gives no ablation or explicit reason for it. A reasonable interpretation is that eight words are long enough to avoid accidental matches on common phrases, and short enough to still catch copied passages.

Why are there two rows in Table 6?

The WebText row on its own is hard to judge. Is 3.94% overlap on text8 a lot? The first row gives the answer by providing a baseline: how much a benchmark's test set already overlaps with its own training split. That overlap is normal and accepted, because test and training splits come from the same source and share common phrases, names and boilerplate.

So the real question is whether WebText overlaps with the test sets more than their own training data does. On average it does not: about 3.2% for WebText versus 5.9% for the benchmarks' own training splits. WebText is higher on only two datasets, WikiText-2 and text8, and even there the overlap is a few percent.

09

Wrapping up

My Learnings

The key lesson GPT-2 is still a weak zero-shot model on most tasks. What it proved is the direction: every curve in the paper goes up with size, and none of them had flattened yet. GPT-3 is what happened when OpenAI followed those curves.
